# Frame-time graph

A small bottom-right diagnostic instanced under DebugOverlay. Enabled by default through `DEBUG/Configuration/DebugMaster.tres`. F2 or the F1 checkbox toggles it. It measures elapsed wall time between process callbacks, keeping 180 frames in a fixed ring buffer. Labels show the mean FPS/frame time and maximum retained frame time; the graph reference is 16.7 ms (60 FPS), with green <=20 ms, amber <=33.34 ms and red above that. Bars clip at 50 ms; the peak label does not. The history spans about three seconds at 60 FPS, with a shorter interval when uncapped. This measures delivered frame cadence, not GPU duration or network latency.

While visible/focused: one timestamp and one buffer write per frame, plus a 5 Hz readout/redraw. No per-frame allocations or world queries. Hidden: Process and redraw timer stop; F2 input remains available. Focus loss suspends sampling and resume resets the timestamp so alt-tab is not treated as a giant frame. Rendering/sampling have a small cost; hide the graph when measuring maximum throughput. The existing five-case report records its visibility and the active FPS cap.

`DebugSettings.FpsCap` defaults to 60; DebugOverlay applies it once on ready and restores the prior Engine.MaxFps on exit. F1 can disable/re-enable the cap without rebuilding grass or terrain. VSync is unchanged and may still limit FPS when the explicit cap is off. A cap limits peak frame rate; it does not remove loading stalls, and a 60 FPS cap is not necessarily the best pacing choice for every refresh rate. The graph helps check the result on the actual display.

Validation: all project C# compiled with Roslyn against the available .NET 8/GodotSharp 4.4.1 API; the configured Godot.NET.Sdk 4.7.2/source-generator project build and visual UI execution remain local checks. Check bottom-right placement, spikes while travelling, F2 hide/show, F1 cap/checkbox synchronization and movement/input, and alt-tab resume. No measured smoothness/FPS improvement is claimed.
